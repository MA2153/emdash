## What does this PR do?

`setupTestDatabase()` ran all 96 migrations for every test, about 110 ms per call. Most core test files call it in `beforeEach`, so migrations took up much of the core suite's time.

The helper now runs the migrations once per test file and dumps the migrated database into a single SQL script. The script holds the schema, then the rows (written with SQLite's `quote()`, so storage classes are preserved), then the indexes and triggers. Each new in-memory database replays that script, which takes about 9 ms.

- Tests that exercise migrations still call `createTestDatabase()` and `runMigrations()` directly.
- The PostgreSQL helpers, `setupTestDatabaseWithCompoundSelectLimit()` (which records every prepared statement) and the other Vitest configs are unchanged.
- `setupForDialect("sqlite")` and the `*WithCollections` helpers get the speed-up, because they call `setupTestDatabase()`.
- A new test, `tests/unit/database/test-db-template.test.ts`, keeps the template from drifting. It compares a restored database with one migrated from scratch: schema objects, every row with its storage class, and the `user_version`, `application_id` and `foreign_keys` pragmas. Timestamps are masked, because the template's rows were written when it was built. Removing indexes and triggers from the dump makes this test fail.

I also tried building the template once in a Vitest global setup and passing it to workers with `provide`/`inject`. It was no faster than building it once per file (131 s against 121 s on a 178-file subset), so I left it out.

`node:sqlite`'s `serialize()`/`deserialize()` would also work, but they are newer than Node 22, which CI runs, so this uses a plain SQL script instead.
